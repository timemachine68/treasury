# สถาปัตยกรรมและแนวทางพัฒนาต่อ — คลังแนะแนว (treasury)

> เอกสารนี้สรุปรูปแบบที่ระบบใช้อยู่จริงตอนนี้ และวางแนวทางว่าฟีเจอร์ใหม่ๆ
> ควรเขียนแบบไหน เพื่อให้ไฟล์ไม่บวมและดูแลง่ายในระยะยาว — ไม่ใช่กฎตายตัว
> ปรับได้เมื่อสถานการณ์เปลี่ยน แต่ให้ใช้เป็นค่าเริ่มต้นเวลาตัดสินใจ

---

## 1. สถานะปัจจุบัน (สรุปสั้นๆ)

- **Single-file HTML ต่อฟีเจอร์** ไม่มี build step, deploy ตรงจาก GitHub Pages
  (`timemachine68.github.io/treasury/<ไฟล์>.html`)
- **`index.html`** เป็น "ศูนย์กลาง": ล็อกอิน, เมนูรวม, โปรไฟล์จุดแข็ง RIASEC,
  ภาพรวมนักเรียน 360°, ประกาศ, จัดการสิทธิ์เมนู — ไฟล์นี้ใหญ่ขึ้นเรื่อยๆ
  (โค้ด JS ในไฟล์เดียวตอนนี้เกิน 100,000 ตัวอักษรแล้ว)
- **ฟีเจอร์ระบบย่อยแต่ละตัว แยกไฟล์ของตัวเอง** อยู่แล้วเป็นส่วนใหญ่ เช่น
  ทุนการศึกษา (`scholarship-*.html`), โควตา (`quota-*.html`), ช้างเผือก
  (`chang-phueak-*.html`), ฝึกงาน (`work-permit-*.html`), ผลงานนักเรียน/TCAS
  (`awards-*.html`), ฝึกข้อสอบ TGAT/TPAT (`tgat-prep-*.html`), ฝึกสัมภาษณ์
  (`interview.html`), ทะเบียนกลุ่มเปราะบาง (`vulnerable-*.html`)
- **Backend**: Supabase (Postgres + Auth + Storage) ทุกตารางเปิด RLS,
  ใช้ฟังก์ชัน `SECURITY DEFINER` (เช่น `get_my_role()`, `is_scholarship_officer()`,
  `awards_is_officer()`) เป็นตัวเช็คสิทธิ์แบบข้าม RLS อย่างควบคุมได้
- **เมนูหลัก** ขับเคลื่อนด้วยตาราง `external_systems` (title/url/visible_to/category)
  ไม่ได้ hardcode ลิงก์ไว้ใน `index.html`

## 2. รูปแบบที่ควรยึดต่อไปนี้

### 2.1 ฟีเจอร์ใหม่ → แยกไฟล์ตาม role เสมอ

รูปแบบที่ใช้อยู่แล้วและควรทำต่อ:

| Suffix | ใช้กับ | ตัวอย่าง |
|---|---|---|
| `-apply` / ไม่มี suffix (ฝั่งนักเรียน) | หน้าที่นักเรียนสมัคร/กรอกข้อมูล/ดูสถานะของตัวเอง | `scholarship-apply.html`, `quota-apply.html`, `work-permit-student.html` |
| `-hub` | หน้ารวมขั้นตอนของครู ลิงก์ไปหน้าย่อยอื่น | `scholarship-hub.html`, `quota-hub.html`, `awards-hub.html` |
| `-teacher` / `-admin` | หน้าจัดการ/ตั้งค่าของครูหรือแอดมิน | `chang-phueak-teacher.html`, `scholarship-admin.html`, `tgat-prep-admin.html` |
| `-results` / `-review` / `-registry` | หน้าคัดกรอง/ตรวจสอบ/ผลลัพธ์ | `scholarship-results.html`, `awards-review.html`, `vulnerable-registry-teacher.html` |

**ทำไมถึงควรแยก แทนที่จะยัดเข้า `index.html`:**

1. โหลดเร็วกว่า — นักเรียนไม่ต้องโหลดโค้ดจัดการของครู และกลับกัน
2. ขอบเขตสิทธิ์ชัดต่อไฟล์ — ตรวจสอบ/รีวิวความปลอดภัยง่ายกว่าไฟล์รวมทุกอย่าง
3. แก้ไฟล์หนึ่งไม่กระทบอีกฝั่ง — ลดความเสี่ยง conflict เวลาหลาย session/คนแก้พร้อมกัน
   (เจอมาแล้วในเซสชันนี้: อีกฝั่งแก้ `interview.html`/`quota-teacher.html` พร้อมกับที่แก้ `index.html`)
4. งานที่ให้ AI ช่วยทำต่อ diff เล็กลง เจาะจงง่ายขึ้น

### 2.2 `index.html` = hub ไม่ใช่ที่เก็บฟีเจอร์ใหม่

`index.html` ควรมีแค่:
- ล็อกอิน/เซสชันกลาง, เมนูรวม (`external_systems`)
- โปรไฟล์จุดแข็ง RIASEC, ภาพรวมนักเรียน 360° (เชื่อมสถานะจากระบบย่อยอื่นมาแสดง)
- ประกาศ, จัดการสิทธิ์เมนูครู

**ฟีเจอร์ใหม่ที่เป็น "ระบบย่อย" ของตัวเอง** (มีฟอร์มกรอกข้อมูล, workflow,
role การอนุมัติของตัวเอง) → **แยกไฟล์ใหม่เสมอ** อย่าฝังเข้า `index.html`

**ข้อยกเว้น**: ถ้าเป็นแค่ "ดึงสรุปสถานะ" ของระบบย่อยที่มีอยู่แล้วมาโชว์ใน
ภาพรวมนักเรียน (แบบที่ทำกับ TCASVerified/ทุน/โควตาไปแล้ว) — ใส่ใน `index.html`
ได้ เพราะเป็นการ "เชื่อมข้อมูล" ไม่ใช่สร้างระบบใหม่

### 2.3 เช็คลิสต์ตัดสินใจเร็วๆ: แยกไฟล์ใหม่ หรือ แก้ใน `index.html`?

แยกไฟล์ใหม่ ถ้า...
- มีฟอร์มให้กรอก/ส่งข้อมูลใหม่
- มีสถานะ/workflow ของตัวเอง (draft → submitted → approved ฯลฯ)
- มีหน้าจัดการเฉพาะของครู/แอดมินที่ไม่ใช่แค่ "ดู"

แก้ใน `index.html` ได้ ถ้า...
- แค่ดึงข้อมูลที่มีอยู่แล้วมาแสดงเพิ่มในภาพรวม/แดชบอร์ด
- แก้ auth/เมนู/สิทธิ์ระดับกลางที่ทุกหน้าใช้ร่วมกัน

## 3. Backend / Supabase — สิ่งที่ต้องทำทุกครั้งที่มีตาราง/ฟังก์ชันใหม่

1. **เปิด RLS ทุกตารางใหม่เสมอ** ไม่มีข้อยกเว้น
2. **ฟังก์ชันที่ต้อง bypass RLS** (เช่น สรุปรายงานข้าม role, เขียนแทนคนอื่น)
   → ต้องเป็น `SECURITY DEFINER`, `SET search_path = 'public'`, และ **เช็ค role
   ภายในฟังก์ชันเองด้วย** (`raise exception` ถ้าไม่ผ่าน) — อย่าพึ่ง RLS ของ
   ตารางที่ query ข้างในอย่างเดียว เพราะฟังก์ชัน definer จะ bypass RLS นั้นไปเลย
   ตัวอย่างอ้างอิง: `counseling_annual_report()`, `scholarship_annual_summary()`
3. **`REVOKE ALL ... FROM PUBLIC, anon`** แล้ว **`GRANT EXECUTE ... TO authenticated`**
   เท่านั้น — ⚠️ โปรเจกต์นี้มี default privilege ที่ grant `EXECUTE` ให้ `anon`
   อัตโนมัติทุกฟังก์ชันใหม่ ต้อง revoke จาก `anon` ตรงๆ ด้วย แค่ revoke จาก
   `public` เฉยๆ ไม่พอ (เจอบั๊กนี้มาแล้วตอนทำ `scholarship_annual_summary()`)
4. **View ที่มีข้อมูลอ่อนไหว** (ชื่อ-สกุล, เลขประจำตัว, ที่อยู่ ฯลฯ) **ห้าม grant
   SELECT ให้ `anon`/`authenticated` ตรงๆ** ให้เข้าถึงผ่าน RPC ที่เช็คสิทธิ์เท่านั้น
   (`v_scholarship_awards`/`v_scholarship_annual_summary` เคยเปิดให้ `anon`
   อ่านตรงๆ มาก่อน แก้ไปแล้วใน PR #8)
5. **เพิ่ม migration file** ใน `supabase/migrations/YYYYMMDD_<ชื่อ>.sql` ทุกครั้ง
   ที่เปลี่ยน schema แม้จะ apply ตรงผ่าน Supabase MCP ก็ตาม — เพื่อ track
   ประวัติไว้ใน repo ให้ตรงกับฐานข้อมูลจริง
6. **query ที่มีโอกาสเกิน 1,000 แถว** ต้อง paginate ด้วย `.range()` เสมอ
   (ข้อจำกัดของ PostgREST) — หรือย้ายไปทำเป็น RPC ที่คืนค่าสรุป/JSON แทน
   การ `.select("*")` ตรงๆ (แบบที่ทำกับ `scholarship_annual_summary()`)

## 4. Navigation

ฟีเจอร์ใหม่ทุกตัว (โดยเฉพาะหน้าแรกของ flow ที่ role นั้นควรเจอ) ต้อง
**ลงทะเบียนในตาราง `external_systems`** (title, url, visible_to, category)
ไม่งั้นจะเข้าถึงได้แค่ผ่านลิงก์ตรง/หน้า hub เท่านั้น ผู้ใช้ทั่วไปจะไม่เห็นในเมนู

## 5. หน้ารายงาน/ข้อมูลอ่อนไหว — ตรวจสิทธิ์ก่อนขึ้นจริงเสมอ

ทุกหน้าที่โชว์ข้อมูลรวมของนักเรียนหลายคน (รายงาน, สรุปรายปี, export) เฉพาะ
role ใด role หนึ่ง ควรทำหน้า `debug.html`-style access check ก่อน merge:
- ทดสอบเป็น anon (ไม่ล็อกอิน) ว่าเข้าไม่ได้จริง
- ทดสอบด้วย role ที่ไม่ควรเข้าได้ (เช่น นักเรียน) ว่าถูกบล็อกจริง
- ยืนยันด้วย SQL จำลอง role ผ่าน Supabase MCP ก่อน merge ทุกครั้ง (ไม่ใช่เดาจาก
  โค้ดอย่างเดียว) — ดูตัวอย่างใน `debug.html` และ PR #8

## 6. เมื่อ `index.html` เริ่มใหญ่เกินไป — สัญญาณเตือน + ทางแก้ระยะยาว

**สัญญาณที่ควรเริ่มคิดเรื่องแยกไฟล์จริงจัง:**
- โหลดช้าเห็นได้ชัดบนมือถือ/เน็ตช้า
- แก้ไฟล์แล้ว conflict บ่อยเพราะหลาย feature ต้องแก้ไฟล์เดียวกัน
- หาฟังก์ชัน/ตัวแปรในไฟล์ยากขึ้นเรื่อยๆ

**ทางแก้ระยะยาว (ยังไม่ต้องทำตอนนี้ ทำเมื่อสัญญาณข้างต้นเริ่มชัด):**
1. **แยก shared script ออกมา** — โค้ดที่ใช้ร่วมกันหลายหน้าอยู่แล้ว (เช่น
   `esc()`, ธีมสี, RIASEC data, รูปแบบ auth login) ย้ายไป `shared.js`/`shared.css`
   แล้วให้ทุกหน้า `<script src="shared.js">` — ไม่ต้องมี build step ก็ทำได้
   ลดการ copy-paste ซ้ำระหว่างไฟล์ (ตอนนี้ auth boilerplate ซ้ำกันแทบทุกไฟล์)
2. **แยก `teacher.html` / `student.html` จาก `index.html`** — ทำเป็นขั้นสุดท้าย
   เพราะกระทบเยอะที่สุด (ต้องแยก routing, session, เมนูออกจากกัน) ควรทำ
   หลังจากข้อ 1 นิ่งแล้วเท่านั้น
